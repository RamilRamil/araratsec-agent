# Анализ статьи: The Audit Gap in Blockchain Security

## Метаданные
- **Название**: The Audit Gap in Blockchain Security
- **Авторы**: Stefan Beyer
- **Год / Venue**: 2026, arXiv (период данных: январь 2022 — март 2026)
- **arXiv / DOI**: 2606.15465 — https://arxiv.org/abs/2606.15465
- **Источник**: blockthreat.com newsletter

---

## 1. СУТЬ

Сопоставление 23 818 находок аудитов (22 фирмы) с 218 реальными эксплойтами (~$7.76 млрд потерь) показывает: аудиты и реальные потери описывают **разные явления** с непересекающимися распределениями — топ-3 категории находок дают 3.8% потерь, а human-vector атаки, почти отсутствующие в находках, дают 49.6% потерь.

---

## 2. МЕТОД

**Тип работы**: эмпирический анализ двух корпусов данных, без ML-метрик и baseline.

**Данные**: 23 818 находок аудитов от 22 фирм + 218 инцидентов с потерями за 4 года.

### Что находят аудиты (по частоте)

| Категория | % находок |
|---|---|
| Logic / Business Logic | 14.6% |
| Code Quality | 13.0% |
| Input Validation | 10.0% |
| Access Control | 9.8% |
| Initialization / Upgradeability | 7.3% |
| Integer Overflow | 5.4% |
| Oracle / Price Manipulation | 4.3% |
| **Reentrancy** | **2.1%** |

Доля Critical+High стабильна: 15–17% в год все 4 года.

### Что вызывает реальные потери (по объёму денег)

| Root cause | Потери | % от общих | Средний инцидент |
|---|---|---|---|
| Private Key Compromise | $1 894M | 24.4% | $42.1M |
| Phishing / Social Engineering | $1 511M | 19.5% | $125.9M |
| Access Control | $994M | 12.8% | $33.1M |
| Oracle / Price Manipulation | $666M | 8.6% | $15.5M |
| Bridge Exploit | $593M | 7.6% | $148.3M |
| Signature / Replay | $516M | 6.6% | $258.0M |

**Human-vector атаки** (ключи, фишинг, supply chain, governance): 65.6% годовых потерь в 2023, 74.6% в 2024, 70.8% в 2025, **49.6% кумулятивно**.

### Разрыв в цифрах

Топ-3 категории находок (logic, code quality, input validation) = 37.6% находок → лишь **3.8% потерь**.
Human-vector атаки = пренебрежимая доля находок → **49.6% потерь**.

### Почему разрыв существует

> «Обычный аудит смарт-контракта проверяет исходный код определённого коммита в рамках определённого scope. Он не проверяет среду деплоя, практики управления ключами подписантов, CI/CD-пайплайн, хостинг фронтенда и цепочку поставок сторонних зависимостей.»

Из 12 крупнейших инцидентов у **уже проаудированных** протоколов у 9 root cause лежал вне scope аудита. Пример: Bybit ($1.43 млрд) — фишинг подписантов при проаудированном контракте.

### Концентрация потерь

- Топ-8 инцидентов = 50.6% кумулятивных потерь, топ-20 = 71.4%
- Ethereum + BNB Chain = 89% инцидентов, 94% потерь
- Распределение тяжелохвостое — гауссовы модели риска недооценивают хвост

| Тип протокола | Инцидентов | Потери | Средний инцидент |
|---|---|---|---|
| CEX | 24 | $2 284M | $95.2M |
| Bridge | 22 | $2 401M | $109.1M |
| Lending | 48 | $736M | $15.3M |
| DEX | 31 | $603M | $19.5M |

Мосты и CEX — наибольшие средние потери на инцидент.

## 3. СКЕПТИК

**Насколько доверять числам:**

- **Сравниваются разные единицы измерения.** Находки считаются по частоте, потери — по деньгам. Категория может быть редкой в находках и при этом дорогой — это не обязательно «провал аудита», а свойство несопоставимых шкал. Автор частично признаёт это, но вывод «аудиты ищут не то» из этого прямо не следует.
- **Выжившие не видны.** Потери от багов, **пойманных** аудитом, ненаблюдаемы по построению. Низкая доля reentrancy в потерях может означать, что с ней научились справляться, а не что она неважна.
- **Таксономии двух корпусов не выровнены.** Категории аудиторских находок (22 разные фирмы, разные внутренние классификаторы) и root cause инцидентов приводились к общему списку — процедура сопоставления критична и в реферате не детализирована.
- **Атрибуция root cause постфактум.** Инцидент часто имеет цепочку причин; выбор одной «главной» — это суждение аналитика.
- **Концентрация делает выборку хрупкой.** Топ-8 инцидентов = половина всех потерь; сдвиг атрибуции одного Bybit ($1.43 млрд) заметно двигает всю картину human-vector.

**Вывод по доверию**: методологические оговорки существенны, но **основной вывод устойчив** — аудит кода не покрывает операционную безопасность, и это подтверждается независимо ([[blockaid-private-key-compromise-2026]]). Цифры стоит использовать как порядок величины, не как точные веса приоритетов.

## 5. РЕШЕНИЕ

**5.1 Что статья подтверждает**

- Наш pipeline Stage 1–3 покрывает уязвимости кода — необходимо, но недостаточно
- Таксономия `BastetTag` (46 тегов) адекватна для анализа слоя кода
- Reentrancy (2.1% находок) не должна доминировать во внимании Stage 2

**5.2 Impact map должен покрывать не-кодовые векторы**

`AuditInput.impact_targets` (предложено в [[pkqs91-codex-bounty-workflow]]) должен включать:
- `loss_of_funds_via_contract` — покрыто текущим pipeline
- `private_key_compromise` — требует оценки key management
- `governance_manipulation` — требует анализа on-chain governance
- `bridge_exploit` — требует анализа cross-chain trust boundary

Разные impact targets → разная приоритизация инструментов.

**5.3 Тип протокола меняет профиль риска**

Мосты: в среднем $148M на инцидент — высший приоритет для проверок cross-chain trust boundary.
CEX: риск ключей/кастодиальный > риск смарт-контракта.

Приоритизация SIG в Stage 1 должна взвешиваться по типу протокола, а не только по сложности кода.

**5.4 Декларация scope в отчёте**

Финальный отчёт должен явно перечислять, что НЕ оценивалось: управление ключами, workflow подписантов, целостность CI/CD, хостинг фронтенда, цепочка поставок зависимостей. Это прямо следует из вывода статьи и согласуется с `docs/eval-principles.md`.

**5.5 Reentrancy — не тот приоритет, что раньше**

Теги `reentrancy`, `read_only_reentrancy`, `cross_function_reentrancy` держать нужно, но распределение времени Stage 2 не должно перевешивать их относительно oracle manipulation, access control и cross-chain trust boundaries.
