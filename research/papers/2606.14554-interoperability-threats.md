## Метаданные
- **Название**: Security Threats and Their Impact on Blockchain Interoperability
- **Авторы**: Shawn M. Reynolds, Hassan Reza (University of North Dakota)
- **Год / Venue**: 2026, arXiv
- **arXiv / DOI**: 2606.14554 — https://arxiv.org/abs/2606.14554
- **Источник**: blockthreat.com newsletter

---

## 1. СУТЬ

Систематизация 38 атак на интероперабельные блокчейн-системы в 5 категорий с сопоставлением каждой атаки её impact и контрмерам — даёт готовый словарь угроз для аудита мостов и cross-chain протоколов, включая 6 атак, специфичных именно для интероперабельности.

---

## 2. МЕТОД

**Тип работы**: обзорная/систематизирующая (survey). Метрик, датасетов и экспериментов нет — это таксономия, построенная по литературе и реальным инцидентам.

### Таксономия из 5 категорий

**A. BC Attacks (12)**

| Атака | Impact |
|---|---|
| 51% Attack | Контроль консенсуса, мошенничество |
| Sybil Attack | Срыв консенсуса, DoS |
| Double-Spending | Мошенническая трата |
| Block Withholding | Срыв майнинга, потеря награды |
| Selfish Mining | Несправедливые награды, возможный форк |
| Fork After Withholding | Форк, кража награды |
| Private Key Leakage | Захват аккаунта, потеря средств |
| Nothing at Stake | Захват блокчейна |
| Time-Jacking | Double-spending, трата ресурсов |
| Replay Attack | Дублирование транзакций |
| Transaction Malleability | Double-spending, кража средств |
| Reentrancy | Финансовая эксплуатация |

**B. Network Attacks (7)**: DoS/DDoS, Botnet, Packet-Dropping, Stopping Attack, Eclipse Attack, Partitioning, Man-in-the-Middle.

**C. Атаки, специфичные для интероперабельности (6)** ← самое релевантное для аудита мостов

| Атака | Реальные примеры | Impact |
|---|---|---|
| Relay Poisoning | ETH Relay | Мошеннические cross-chain транзакции |
| Oracle Poisoning | одноисточниковые оракулы | Потеря средств, несправедливая ликвидация |
| Goldfinger Attack | новые сайдчейны | Форк, double-spending |
| Sore Loser / Lockup Griefing | атомарные свопы | Активы заблокированы бессрочно |
| Unrestricted Deposit Emitting | Multichain, Meter.io | Double-spending без блокировки |
| Unauthorized Unlocking | Anyswap | Double-spending через украденные ключи |

**D. Social Engineering (3)**

| Атака | Примечания |
|---|---|
| Social Engineering | выдача себя за другого, pretexting, whaling |
| Phishing | клоны сайтов, фейковые ICO, вредоносные кошельки |
| Homograph Visual Cognitive Deception | Unicode-омоглифы в адресах/коде; 50% успеха на аппаратных кошельках |

**E. Vulnerabilities (10)**: Smart Contract Vulns, Public Key Crypto Vulns, Improper Value Validation, Visibility Vulnerability, Weak Randomness, Transaction Order Dependence, Asset Counterfeiting, Verifier's Dilemma, Invalid Consensus Proofs, Inconsistent Event Parsing.

### Паттерны контрмер

- Системы мониторинга/детекции: закрывают 11+ различных угроз
- Техники валидации: предотвращают replay и атаки на консенсус
- Механизмы временных меток: защита от атак на время
- Репутационные системы: сдерживают Sybil, eclipse, Goldfinger
- Аудиты кода: предотвращают уязвимости смарт-контрактов до деплоя

**Отдельные контрмеры:**
- **Reentrancy**: паттерн Check-Effects-Interactions; mutex-локи; статический/динамический анализ; фаззинг.
- **Oracle Poisoning**: агрегация нескольких независимых оракулов; механизм оспаривания; финансовые стимулы за точность.
- **Unrestricted Deposit Emitting**: требовать верифицированное событие блокировки до любого депозита; только безопасные функции перевода; автоматическая детекция по паттернам.
- **Homograph Deception**: обучение пользователей проверять полный адрес и контрольную сумму; автоматический мониторинг; сверка селекторов функций через hex-просмотр.
- **Weak Randomness**: заменить небезопасные источники (хеш блока, timestamp) на RANDAO или RBGC.
- **Transaction Order Dependence**: схема commit-reveal — скрывать решения до обработки, предотвращая front-running.

## 3. СКЕПТИК

**Насколько доверять числам:**

- **Числа здесь — размеры списков, а не измерения.** «38 атак в 5 категориях» отражает выбор границ обзора; другой автор получил бы другое число. Проверять нечего, но и опираться на полноту нельзя.
- **Категории пересекаются и разноуровневые.** Private Key Leakage стоит в BC Attacks, хотя это операционная безопасность; Reentrancy — и в BC Attacks, и фактически в Vulnerabilities. Категория E («Vulnerabilities») — это класс дефектов, а A-D — классы атак; смешение уровней мешает использовать таксономию как классификатор.
- **50% успеха homograph на аппаратных кошельках — единственная конкретная цифра, и она вторичная** (пришла из цитируемой работы). Условия эксперимента и выборка в обзоре не приводятся.
- **Контрмеры перечислены, но не оценены.** Нет данных о том, насколько они действительно снижают риск и чего стоят; «аудиты кода предотвращают уязвимости» — тезис, который [[2606.15465-audit-gap]] существенно ограничивает эмпирически.
- **Нет привязки к объёму потерь.** Список угроз плоский: relay poisoning и block withholding идут наравне, хотя их вклад в реальные потери отличается на порядки.

**Вывод по доверию**: как источник **словаря и структуры** — полезно и малорискованно; как источник **приоритетов** — не годится, приоритеты брать из данных о потерях ([[2606.15465-audit-gap]], [[blockaid-private-key-compromise-2026]]). Категория C — главная практическая ценность работы.

## 5. РЕШЕНИЕ

**5.1 Что `BastetTag` покрывает и чего не хватает**

Покрыто:
- reentrancy, read_only_reentrancy, cross_function_reentrancy ✓
- oracle_manipulation, price_manipulation, flash_loan_attack ✓
- frontrunning, sandwich_attack, mev (→ tx_order_dependence) ✓
- signature_replay ✓
- access_control, missing_access_control ✓

Не хватает — специфичное для интероперабельности (нет среди текущих 46 тегов):
- `relay_poisoning` — подложные заголовки блоков в cross-chain relay
- `unrestricted_deposit_emitting` — депозит без соответствующей блокировки на источнике
- `unauthorized_unlocking` — разблокировка без авторизации исходной цепочки
- `inconsistent_event_parsing` — парсер cross-chain событий неверно считает активы
- `lockup_griefing` — бессрочная блокировка активов через брошенную транзакцию

Не хватает — общее:
- `weak_randomness` — хеш блока / timestamp как источник случайности
- `asset_counterfeiting` — необеспеченная эмиссия токенов

**Оговорка**: расширять таксономию нужно осторожно — [[pkqs91-codex-bounty-workflow]] прямо показывает, что раздутый список паттернов деградирует в шум. Добавлять только теги с чётко определяемым триггером, и только для bridge-линии.

**5.2 Homograph deception → наш sanitize.py**

Статья подтверждает 50% успешность homograph-атак. Наш `sanitize.py` применяет NFKC-нормализацию, приводящую визуально похожие Unicode-символы к каноническим формам — прямая защита от этого класса. Это валидирует guardrail. Стоит добавить явную детекцию омоглифов (флагировать confusable-символы в адресах и именах функций) как отдельный флаг sanitize.

**5.3 Приоритет bridge-протоколов**

Вместе с выводами [[2606.15465-audit-gap]] (у мостов в среднем $148M на инцидент):
- если `AuditInput` определяет протокол как мост/cross-chain → активировать проверки, специфичные для интероперабельности
- SIG в Stage 1 должен помечать cross-chain trust boundaries как высокоприоритетную поверхность
- 6 категорий атак из раздела C ложатся в выделенную линию Stage 2 для аудита мостов

**5.4 Интеграция с impact_map**

Работа даёт словарь для полей `impact_map`:
```python
impact_targets = [
    "loss_of_funds_via_contract",      # покрыто текущим BastetTag
    "cross_chain_double_spending",     # relay poisoning, unauthorized unlocking
    "oracle_manipulation",             # oracle poisoning
    "asset_lockup",                    # lockup griefing
    "private_key_compromise",          # операционная безопасность (вне scope кода)
]
```
